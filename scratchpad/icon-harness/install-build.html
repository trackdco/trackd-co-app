The button
One action, nothing else. Add to home screen fires Chrome's real install prompt on Android; on iOS there is no such API, so it opens the walkthrough. No "I understand", no skip — installing is how notifications work, so the escape hatch moves to the walkthrough and gets small.
Everything else
The surrounding apps are drawn, not screenshotted — recognisable by colour and shape without shipping anyone's artwork. They sit at 32% so the eye lands on Kyle.

The slam-in is kept and is now the only motion on the screen — nothing else competes with it.

Because there is no way out here, the walkthrough that follows must always offer one. A screen that cannot be left is a screen people close the tab on.

Does the app actually know which of these to show?

Partly. The panel above runs the shipped code — guessPlatform and guessBrowser copied out of lib/onboarding/platform.ts — so what it reports about your device is what the real screen would decide. Here is what it gets right and what it does not.

  • Browser: yes. Chrome on iPhone is detected (CriOS), and so are Firefox (FxiOS), Edge (EdgiOS) and Samsung Internet. The order of those tests matters and is already correct — every iOS browser carries "Safari" in its user agent, so the specific tokens have to be checked first.
  • Handset: no, and this is the real gap. The app knows iOS from Android and nothing more. It cannot tell a Galaxy from a Pixel, so it has no way to pick between the Samsung home screen and the Google one. Both are drawn here and neither can currently be chosen automatically. It is a small fix — SM- and Pixel are both in the user agent, and the panel above proves it by doing exactly that — but it is not in the app yet. Say the word and I will add it.
  • Desktop: silently called an iPhone. guessPlatform ends in return "ios", so anyone on a laptop is shown Safari's Share sheet. Harmless during onboarding on a phone, wrong the moment somebody opens the link on a computer.
  • Not detected at all: Opera, Brave, DuckDuckGo, Vivaldi. On Android they all install fine and would fall through to the Chrome path, which is close enough to right. On iOS they cannot install, and they would be told they can — that one is worth fixing alongside the handset check.

Which phones are covered

  • iPhone — iOS 26 Liquid Glass throughout: the floating tab-bar capsule, the separate tabs button, the translucent More menu, the share sheet and the confirmation sheet, plus a glass dock and search pill on the Home Screen.
  • Google Pixel — the Google phone, drawn as its own skin: circular icons, the at-a-glance line, the Google search bar, and Gemini in the dock where Assistant used to be.
  • Samsung Galaxy — One UI: its own grid, rounded-square icons, the clock block, SmartThings and Galaxy Store, and Samsung Internet's bottom tray rather than a top-right menu.
  • Everything else on Android — OnePlus, Motorola, Xiaomi and the rest run their own launchers, but the browser flow is identical to Chrome's, which is the only part these recordings teach. They get the Pixel skin as the stand-in. If you want a fourth skin, say which handset and I will draw it.

If you want it shipped, this is the order

  • First, on its own: the Android bug. appinstalled already fires and is already listened to — the handler just discards it, so anyone who installs from Chrome's own menu is thrown into the iPhone Share-sheet instructions. Make the flag sticky, move the check above the Android branch. About five lines, no new UI, and it is live on your most-instrumented platform right now.
  • Then the screens above: a tab-return hook (visibilitychange + pageshow), the ask, the obsolete-tab screen, and swapping install.tsx's private standalone check for the getCapability() that already exists in lib/push/pushService.ts. There are currently two copies of that predicate.
  • Then wire up the column that already exists. When the installed app first launches and signs in, stamp profiles.pwa_installed_at. The browser tab is still signed in as the same user, so it can read that flag and know — for certain, across the container boundary, on iOS, with no API and no guessing. Highest value per line on the list, and the migration is already applied.
  • Last, and only if you want it: the manifest nonce. Needs your sign-off and a real-device test.

Two things I'd check on a real handset

  • The Safari sequence is drawn from your description of your own phone — ⋯, Share, View More, Add to Home Screen, Add. Run it once and tell me if a frame is off; it is defined in one place, so a correction lands everywhere at once.
  • The Chrome-on-iPhone claim. The app states only Safari can install on iOS and the path is drawn that way, ending in the black stop screen and then the full Safari steps. Apple has been loosening third-party browser rules, so it is worth two minutes before launch.
